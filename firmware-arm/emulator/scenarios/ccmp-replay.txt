# A captured CCMP frame, sent again -- counted, not refused.
#
# CCMP's integrity check says a frame is genuine; only the receiver's record
# of the last packet number (PN) it took says a genuine frame is not being
# played a second time. The stock driver kept none: the radio decrypts the
# copy as it did the original and ieee80211_input_data hands it up again.
# Without ccmp_replay_count the first `expect-replay` fails ("this build has
# no ccmp_replay_count step") and the transcript shows the replayed frame
# delivered: that is the control.
#
# The step counts what a replay check would refuse and refuses nothing,
# because what the RT2571W writes in the RXD's Iv and Eiv words has never
# been read on a rabbit (the virtual AP fills them as Linux's rt73usb says
# the chip does: the stripped CCMP header). This scenario is the check's
# logic, on that assumption:
#
#   ordinary traffic, unicast and group interleaved        0 counted
#   the last unicast frame again                           1 unicast
#   the last group frame again                             1 group
#   a retransmission (same PN, Retry bit)                  counted apart
#   a group rekey, twice (the key id alternates)           no false positive
#   a pairwise rekey: the new key's PN starts at 1         no false positive
#   message 3 retransmitted: no key installed, the PN
#   goes on, and a replay after it is still seen           1 more unicast
#
# and every frame is still handed up (expect-data-up counts the copies too).
# scenarios/enforce/ccmp-replay.txt is the same traffic with the refusal on.

ap 02:00:5e:10:00:01 Terrier 6 wpa2-ccmp -52
psk nabaztag
tick 50
stop 100000
