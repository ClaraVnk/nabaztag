# A WPA3-only network, and a rabbit whose config page holds no passphrase.
#
# This is the scenario that was missing, and the bug it would have caught is
# the one a real UniFi found on 2026-11-06.
#
# SAE needs the password itself. patch_wpa3_sae captured it in netPmk(), on
# the grounds that it is the only place it passes through C -- but netPmk runs
# when the password is TYPED, in the config-mode form handler, not when the
# rabbit boots. Every boot after that reads the cached PMK out of the config
# sector and hands THAT to netAuth, so ieee80211_sae_pw was empty,
# ieee80211_sae_begin() returned 0 at its first line, and the SAE branch fell
# through to open auth + PSK. On a WPA3-only network the rabbit simply never
# authenticated: the first belly light blinked orange for ever.
#
# The emulator could not see it, because the harness called
# ieee80211_sae_password() itself. It now reads offset 92 of the config page
# the way the patched wifiAuth does -- and this scenario deliberately boots
# with NO config page at all, so there is nothing to read.
#
# Expected outcome: no association. There is no PSK path on a WPA3-only AP,
# so a rabbit that cannot start SAE has nowhere to go. If this ever reaches
# RUN, something is supplying a password that the firmware does not have, and
# the WPA3 scenarios next door have gone back to proving nothing.
#
# It stops in AUTH rather than IDLE, which is worth knowing on its own: when
# ieee80211_sae_begin() fails, rt2501_auth sets state back to IDLE and then
# falls through and sends an ordinary open-authentication frame -- so the
# rabbit does transmit, and does advance to AUTH, waiting for a reply a
# WPA3-only AP will never send. From the outside that is the first belly
# light blinking orange for ever, which is exactly what the hardware did.
# Hence expect-not RUN: the state it lands in is an implementation detail,
# the association never completing is the property.

ap 02:00:5e:10:00:01 Terrier 6 wpa3-sae -52
psk nabaztag
tick 50
stop 30000

at 20000 expect-not RUN
