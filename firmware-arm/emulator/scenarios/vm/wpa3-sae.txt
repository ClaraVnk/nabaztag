# A whole rabbit, driven by its own bootloader bytecode, onto a WPA3-only AP.
#
# For ./rabbit-vm built with BYTECODE pointing at boot.0.0.0.13.bin — the
# bootloader, not the bytecode a warren serves. That distinction is the whole
# point of this scenario: wifiAuth, the netSaePw call that hands SAE the
# stored passphrase, and the boot URL all live in the bootloader, and until
# 2026-11-07 nothing outside a real rabbit had ever executed them. Two WPA3
# bugs in two days lived in exactly that gap.
#
# The EEPROM says wpa2 on purpose. The config form writes the passphrase to
# offset 92 whatever the security mode, and the rabbit's own netAuth check
# compares the scan's cipher against the stored one; what makes this a WPA3
# association is the AP, not the configuration.
#
#   python3 mkconf.py --ssid Terrier --psk nabaztag --security wpa2 \
#     --server localhost:18080/vl -o rabbit.eeprom
#   ./rabbit-vm scenarios/vm/wpa3-sae.txt --eeprom rabbit.eeprom --warren localhost

# `bytecode: bootloader` below is read by tools/vm-check.sh: this scenario
# runs under the VM given with --boot-vm, and is reported SKIP without one.
# Under a VM linked with a warren's .hybrid it ends in IDLE -- that
# bytecode's wifiAuth has no netSaePw, so SAE has no password and the
# driver falls back to open authentication, which a WPA3-only AP refuses
# (status 13). Measured 2026-11-08; it is not a firmware fault.
#
# bytecode: bootloader

ap 02:00:5e:10:00:01 Terrier 6 wpa3-sae -52
psk nabaztag
tick 50
stop 120000

at 20000 expect RUN
